## Retained-source restoration, cleanup, and readiness oracles

These properties execute through `zfs-guest`/ordinary `driver.py`, not `guest-backups`. They reuse the same physical host resources, source-built release/image, pool and terminal path.

- Restoration dispatch is explicit in `probe.exs:252-265`. `driver.py:123-136` starts/writes VM 104, records native dataset GUID, invokes `restore-cancelled-source`, reads exact old marker, requires unchanged dataset GUID, absent `@lilly-b`, retained positive allocation, and later deletion clears allocation. `driver.py:138-143` repeats the zero-snapshot cancellation/tombstone leg for VM 105.
- Fixture contract `restoration.exs:7-14` requires typed export revocation and physical stop before new epoch, unchanged disk/snapshot GUIDs, fresh ready boot, stale-launch refusal and snapshot-only cleanup, while explicitly disclaiming Marshall coordination/destination reclamation. Actual source is stopped before single full snapshot (`:18-25`); snapshots/no-snapshot case is asserted (`:28-31`). Revocation is replayed with identical receipt (`:41-42`); stop at successor epoch is physically observed false (`:43-45`). Restored start/running waits each 30 s (`:46-47`). Ready boot and boot challenge must both change, epoch=2/generation=3, unchanged snapshot index, and old epoch=1 even generation=99 must refuse while current ready boot remains exact (`:48-55`).
- Snapshot-only cleanup requires retained dataset GUID, retired journal, original relocation/epoch binding, all slots deleted, and exact new boot/guest still ready (`restoration.exs:57-66`). Native slot checker ensures each retained slot GUID agrees with real ZFS owner inventory and each deleted slot is natively absent (`:157-174`). Bad cleanup epoch and expired lease refuse; valid cleanup and replay return identical receipt (`:139-151`, await 300 s). Synthetic Store/runtime is explicit at `:106-137` with `fixture.invalid` client; no transport/fleet authority is exercised.
- Logical Delete snapshot retry: `driver.py:145-150` invokes VM 106 cleanup and requires native dataset and allocation absent. `restoration.exs:70-103` first stops/captures, requires ordinary delete initially errors while unit is stopped and durable intent deleted at same epoch/generation, rejects stale starts, performs authenticated snapshot cleanup to retired, repeats identical delete successfully and rejects later start. `probe.exs:552-568` retries restored-source delete only on explicit cleanup-unconfirmed with unchanged epoch=2/generation=4 and fixed 60 s deadline; other errors do not become success.
- Activation-bound readiness is a separate NixOS-only ordinary driver case (`driver.py:117-121`, probe dispatch `probe.exs:271-273`). `readiness.exs:8-12` explicitly limits synthetic relocation descriptor to a real confined guest/readiness effect, not transfer/Marshall/full move. `:90-109` requires canonical boot UUID, continuity after a brief real placement lock, failure within 50 ms probe budget when lock persists, later continuity, wrong generation/command UUID/expired request refusals, and refusal once the guest physically stops. Lock holder sleeps 250 ms and releases in `after` (`:127-164`); cleanup uses same authority and a 60 s bound (`:167-183`).

Physical confinement is reached by every `zfs-guest observe` and start/running call. `probe.exs:459-461` requires `Observation.running?` then production adoption. `lilly/lib/lilly/vm/observation.ex:15-28` requires exact cgroup VMM, jail root, network namespace, executable identity, resource limits and Firecracker API; `:42-46` verifies VM UID/GID, zero effective caps, no-new-privileges, seccomp mode 2 and inner PID 1; `:52-63` verifies CPU max, exact host-memory max and zero swap. These are native Linux/runtime boundaries reached by the fixture, not escape resistance or independent-host isolation proof. Terminal reads/writes authenticate persisted current epoch/generation and boot via vsock (`probe.exs:702-729`) without reporting terminal bytes.
