# Product context and observable journeys

## Summary

Overalls provides persistent development machines whose usefulness depends on more than successful provisioning. A user signs in, creates or launches a machine, works through a browser terminal, personal editor or SSH, and expects files and identity to survive stop/start, resizing, copying and moving. Marshall owns intent/access; Lilly owns native execution; Audi supplies naming and ingress; Porsche and Lyra expose management and guest tooling. This division is explicitly described in `marshall/priv/hldd/01-system.md:14–16,53–70`. The authenticated browser surface includes Workspace, machines, teams, integrations, usage, agent threads, security and Control room (`marshall/lib/marshall_web/router.ex:94–129`).

The failure hypotheses below are research candidates, not findings that a guarantee holds or a defect exists. Source paths and line numbers identify implementation seams and intended contracts. No runtime checks were performed. P0 means unauthorized access, loss/corruption of retained user data, or authority resurrection; P1 means a core development journey cannot finish; P2 means a supporting workflow or operator diagnosis degrades. Priority reflects impact and workflow centrality, not measured incident frequency.

## 1. Sign-in and usable authority — P0/P1

The user-visible mail-request response deliberately conceals enqueue success or failure. The sender returns `:ok` after either outcome (`marshall/lib/marshall/accounts/user/senders/send_magic_link_email.ex:6–23`), while the outbox validates recipient/token binding and serializes a case-insensitive one-minute cooldown (`marshall/lib/marshall/accounts/auth_emails.ex:9–27,36–75`). A link GET renders an automatic CSRF-protected POST; rendering alone must not consume the link (`marshall/lib/marshall_web/automatic_magic_sign_in_live.ex:7–10,29–33`). The callback verifies the stored login and routes incomplete MFA to Security, including a fixed launch-resume return (`marshall/lib/marshall_web/controllers/auth_controller.ex:23–41`).

Hypothesis: dependency faults can leave a user seeing generic success without receiving usable mail, but cannot turn a request or preview GET into authority. Use an independent SMTP fixture to record acceptance and its issued link, disable browser JavaScript for an initial GET, and independently inventory stored logins before/after the real POST. Check one successful token consumption and refusal of replay. Lose SMTP DATA acknowledgements and database commit replies, restart workers, and compare immutable Message-ID/link bytes; duplicate mail is permitted under uncertainty. ADR-0040 explicitly distinguishes upstream acceptance from inbox placement (`docs/architecture/decisions/0040-host-local-smtp-relay.md:35–43`), so an exactly-once-email oracle would be incorrect.

Hypothesis: sign-out, global revocation, MFA reset and retirement defeat copied cookies across Marshall replicas. ADR-0123 requires remembered exchange/revocation serialization and independent MFA (`docs/architecture/decisions/0123-remembered-browser-authority.md:28–56`). Copy cookies to another browser/replica, commit revocation, exercise mounted and fresh reads/mutations, then partition that replica from PostgreSQL. Observe refusal and unchanged guest/domain effects; a reconnect must not restore old authority.

## 2. Create, retry and become usable — P1, with P0 allocation safety

Creation defaults to OSS in the handbook (`marshall/priv/hldd/07-guests.md:77–86`). The browser parses complete integer sizes and calls Compute with the current actor and retained request key, then reports “Machine requested” (`marshall/lib/marshall_web/live/machines_live.ex:110–147`). Durable admission compares the original request shape/source and commits VM, placement, reservation, address, operation and job together (`marshall/lib/marshall/compute/admission.ex:34–82`). Fresh host/pool evidence and an enabled matching image are admission inputs, not proof of eventual guest usability (`marshall/lib/marshall/compute/admission.ex:143–186`).

Hypothesis: lost replies, duplicated browser events and failover produce one machine per original key; changed shapes refuse. The workload should own a request ledger and expected identity, retry the same request through different replicas, and independently count native placements/processes as well as rows. After faults cease, require a real terminal/SSH command to write and read a unique file. Separate request acceptance, native process running, current physical readiness and usable shell deadlines; an accepted row or green service health alone cannot satisfy this journey. Refusals for stale capacity, unavailable images and oversize disks should leave no partial allocation.

## 3. Repository launch and retained checkout — P1/P0

Public capture is an inert signed-cookie intent. LaunchLive derives actor/source/visit identity, checks expiry, uses ordinary admission, and only then issues a completion receipt (`marshall/lib/marshall_web/live/launch_live.ex:3–8,44–67`). Source2 covers GitHub, GitLab, Codeberg and Bitbucket; only guests resolve or clone. The guest resolver chooses the longest advertised branch/tag, breaks ties toward branches, and handles provider change heads (`lyra/src/workspace_checkout.rs:36–40,63–124,136–197`). The intended boundary keeps checkout/provider failure separate from running/readiness and never inherits source delivery for clones (`docs/architecture/decisions/0157-multi-provider-authenticated-repository-launch.md:121–127`).

Hypothesis: cross-tab sign-in/MFA, receipt loss, expired captures and competing newer captures preserve one authorized visit and do not erase a newer intent. Use real browser navigation plus an independently prepared TLS Git/API fixture with distinct expected commits for default/ref/tag/commit/change. Assert the checkout's actual Git HEAD and known file bytes, rather than echoing stored source fields. Restart the guest after modifying its checkout and require those changes to survive without re-clone. Stop the provider: a machine may remain usable while checkout fails, so require explicit separate results. Existing machine-driver fixture construction deliberately makes revision choices distinguishable (`nix/verification/tests/machines/repository-launch/driver.py:96–138,247–277,301`).

## 4. Terminal continuity and sharing — P0/P1

The terminal workspace opens durable personal sessions and returns ready/pending/failed results; retryable failure keeps the original request (`marshall/lib/marshall_web/live/terminal_live.ex:60–89`). Authority derives the account from the actor, binds default creation to actor/account/VM execution, and avoids replacing closed shells on reload (`marshall/lib/marshall/terminal/authority.ex:8–63`). Kill requires the session owner and current write authority; authoritative guest listing, rather than a failed query, retires absent sessions (`marshall/lib/marshall/terminal/authority.ex:143–191`). Sharing requires the recipient already to have machine access (`marshall/lib/marshall_web/live/terminal_live.ex:128–151`).

Hypothesis: browser or Marshall disconnects cannot duplicate a shell, fabricate its exit, or revive a revoked viewer. Drive two users and multiple tabs, emit numbered deterministic output plus a durable guest file, interrupt relays and reconnect, and compare the expected byte sequence and guest shell/process witness. Slow a viewer while a neighboring writer continues; observe bounded progress/loss indications without accepting reordered fabricated bytes. Revoke sharing/key/login while streams exist: after the defined authority boundary, old streams must stop delivering protected bytes and writing effects; restoring a grant requires fresh admission. A closed browser socket by itself is insufficient—check the guest marker stops changing under old input authority.

## 5. Personal editor and account continuity — P0/P1

Editor launch requires a running VM, supported capability and fresh write authority, then constructs an origin from VM and permanent GuestAccount UUID (`marshall/lib/marshall/editor/authority.ex:35–48`). Approval/exchange binds the same current account/login and consumes code/state atomically; renewal rechecks execution, host session, UID/name, release and origin (`marshall/lib/marshall/editor/authority.ex:80–157,201–223`). Shared profile policy gives Customer SSH/terminal/editor only, while ordinary profiles have egress/sharing/web (`protocol/lib/overalls_protocol/profile_policy.ex:5–14`). Separate personal homes prevent accidental inheritance, not confidentiality against another sudo-capable writer (`marshall/priv/hldd/07-guests.md:17–27`).

Hypothesis: successful redirect/DNS is weaker than a usable workbench. Require actual editing, saving, search, PTY and language diagnostics, then read saved bytes through SSH after broker/worker crashes and stop/start. Two writers must receive distinct origins/cookies and correct native UID/home ownership. After sign-out, foreign-Origin requests, account retirement or execution/release change, old HTTP/WebSockets must refuse within the lease boundary and produce no guest effects. Email changes must preserve the same User's guest identity, while a fresh same-email account receives a different reservation (`marshall/lib/marshall/accounts/guest_accounts.ex:10–38,65–96`). Observe real UID/home/file ownership independently; database equality cannot establish retained-disk behavior.

## 6. Resize, clone, relocation and deletion — P0/P1

These workflows act on valuable retained data. Resize permits CPU/RAM changes and disk growth, with stale drafts requiring explicit review; late telemetry is distinguished from actual shortfall (`marshall/priv/hldd/06-workflows.md:45–68`). Clone UI retains a request key and uses current actor for queue/retry/cancel (`marshall/lib/marshall_web/live/machines_live.ex:195–239`). Activation rechecks provisioning/manage permission and stable source placement before allocation (`marshall/lib/marshall/compute/clone_placement.ex:23–76`). Current relocation is stopped-only: probe before stopping a running source, full-copy transfer, fenced handoff, source deletion after destination readiness (`docs/architecture/decisions/0155-stopped-only-relocation.md:43–62`).

Hypothesis: injected faults between physical effects and receipts preserve the correct original/copy and avoid two active authorities. Create incompressible known data and independent per-drive hashes, record UID/home and stable SSH identity, then resize/copy/move through public controls while duplicating/loss-delaying replies. After clone, divergent writes and source deletion must leave the copy readable. Cancellation before publication/handoff must restore the source and remove only owned destination artifacts; destination failure after handoff must retain the source copy until explicit retry reaches readiness. Observe native datasets, GUIDs, VMMs and guest reads as well as workflow rows. The current lifecycle test already combines retained GUID, unit absence, reservation state and neighboring process preservation (`nix/verification/tests/machines/fleet/scenarios/lifecycle.py:37–99`); reuse that oracle pattern under richer interleavings.

## 7. Naming, network, supporting services and agents — P0/P1/P2

Relocation also moves the user's access route. Existing Audi tests demand unchanged strict SSH configuration, stable names, retained home markers and stale-source refusal (`nix/verification/tests/machines/fleet/scenarios/audi-relocation.py:1–8,50–81,110–145`). Observe fresh authoritative DNS from both replicas, actual HTTPS/SSH through the destination, and refusal at the old endpoint. Merely seeing a new placement is not route convergence.

Hypotheses for supporting development paths: Brady cache recovery serves only complete public objects and does not leak credential/private responses; Galileo and Ziggy stop old leased access after authority withdrawal; agent retries do not repeat uncertain started tools. These are intended user-facing contracts in `marshall/priv/hldd/10-services.md:43–63,107–144,156–165` and `marshall/priv/hldd/11-agents.md:115–133`. Use fixture-owned public/private HTTP bytes and request counters, controlled inference/integration responses, and uniquely counted guest tool effects. Existing agent prompts can wake stopped machines through ordinary admission (`marshall/priv/hldd/11-agents.md:3–6`), so include wake failure and revoked CLI approval. External live-provider reliability remains outside this repository-only evidence.

## 8. Recovery, updates and operator correctness — P0/P1/P2

Backup is an opt-in recovery product: twelve complete manifests, independent host encryption, crash-consistent guest snapshots with best-effort sync, isolated database restore and no automatic historical authority takeover (`docs/architecture/decisions/0070-host-recovery-backups.md:28–51,59–102`). The coordinator attempts guests before PostgreSQL and requires cleanup/no failures before publication (`nix/domains/system/backups/runtime.py:132–208`); retention validates manifest reference closure before deletion (`nix/domains/system/backups/restic.py:256–283`). Hypothesis: interrupted capture/upload/cleanup preserves the last good point and never publishes an incomplete restore. Restore independently generated files and database ciphertext into quarantine; compare bytes, decrypt with the matching keyring, and verify manifest references after retention. Interrupt a later restore component: earlier files may remain, but final manifest must not appear and the partial target must refuse reuse (`nix/domains/system/backups/runtime.py:328–345`). Stopped/unresponsive guests must still be attempted. Newer UID reservations require explicit reconciliation before historical PostgreSQL can serve alongside retained disks (`docs/architecture/decisions/0158-durable-guest-identities.md:106–110`); backup success cannot waive this boundary.

Host update success requires exact candidate activation and live health, preserves guest processes, and does not undo committed migrations (`docs/architecture/decisions/0036-automatic-host-updates.md:31–43,65–87`; carried forward by ADR-0038). Hypothesis: faults around secret publication/activation leave accurate active-versus-healthy status and recover through a corrected revision. Record native VMM identity and guest markers before updating, reject incompatible secrets, and require renewed real terminal/network access afterward. The existing fleet test preserves exact process snapshots across release and credential-only changes (`nix/verification/tests/machines/fleet/scenarios/updates.py:1–49`). Control room retries and retirement require current authority; use stale admin tabs after demotion/expiry and ensure no mutation effects. Maintenance-ready must depend on physically empty hosts and settled holds, rather than successful jobs (`docs/architecture/decisions/0061-maintenance-evacuation.md:49–54`).

The guest CLI updater is a separate journey: it drains active work, switches a bounded verified binary and restores the previous executable when fresh registration fails (`docs/architecture/decisions/0104-private-guest-cli-updates.md:29–44`; `lyra/src/update.rs:420–449,459–463`). Hypothesis: corrupt/interrupted artifacts never execute and a command completes once before replacement. Independently inspect the managed executable digest/inode, durable command effect and current executor fence; a registration-successful binary has no semantic rollback guarantee. Host health recording likewise requires consecutive live checks, not just a candidate being active (`nix/domains/system/auto-update/runtime.py:915–935`).

## Assumptions and open questions

- These are read-only source-grounded hypotheses. Historical review results retain their own revision/scope; no claimed passing execution applies automatically to this combined baseline.
- Product documents conflict: `marshall/priv/docs/commands.md:60` says Inception cloning is unavailable, while current multi-disk contracts cover every drive (`marshall/priv/hldd/05-storage.md:102–107`). `commands.md:73–77` describes bounded relocation downtime; ADR-0155 accepts full-copy proportional downtime (`:102–105`). Treat these as communication gaps pending reconciliation, not a proven execution bug.
- ADR-0157's header says implemented (`:6`), but its evidence section says current Ubuntu pending/partial and notes pre-identity integration captures (`:193–200`). Latest complete combined guest-family acceptance remains a question.
- Updater deadlines must use current configuration: `nix/domains/system/auto-update/default.nix:251–258` adds up to 300 seconds of timer jitter, while ADR-0036's older prose says two seconds (`:34–35`). Do not infer a ten-second correction bound from that historical prose.
- A minimal workload must expose the native guest/storage boundary to make these end-to-end oracles meaningful. A container-only simulated provisioner can test authority/idempotency but cannot establish Firecracker isolation, filesystem preservation or public-provider availability.
- No repository edits, retired Antithesis artifact reads, architecture decision changes or HLDD changes were made. This scratch report has no implementation architecture impact.
