# magic-link-preview-post-mfa-boundary — Magic-link preview and pending MFA cannot grant browser work authority

**Type / priority / confidence:** Safety (`Always`), P0, high confidence in the intended contract and source locations; unimplemented Antithesis candidate. **Planned primary literal message:** **"Magic-link preview and pending MFA cannot grant browser work authority"**. This message is absent from the fresh `existing-assertions.md` scan.

**Property and assertion semantics.** For one valid SMTP-accepted magic link, a plain HTTP GET, including repeated scanner-style previews, must leave its stored `magic_link` token usable and issue no stored `user` login, session cookie, remember credential or authorized work. A real CSRF-protected POST may consume the link once and create a stored login; replay must not create another. If the account has MFA enabled, that new login cannot perform an authenticated work action until a passkey ceremony for that *same login* commits. `Always` evaluates the before-POST and pending-MFA forbidden-effect inventory after each definite operation; a separate `Reachable` can mark a real accepted POST and a separate `Sometimes` can mark successful same-login verification. Those auxiliary messages must be unique if implemented. Do not require a JS browser visit to remain on the GET page: the real page auto-submits. Use a JS-disabled HTTP/client preview to isolate GET and a JS-enabled browser for the normal journey.

**Fault history.** Request a link through public HTTP, wait for the independently recorded local SMTP DATA acceptance, and extract that exact fixture-owned link. Repeat GETs on Marshall A while delaying SMTP DATA ACK or Oban worker commit; inventory `tokens`, `account_auth_emails`, `users` and browser cookies. POST through A with the actual CSRF form while B races a duplicate POST and A loses its response or restarts. Reconcile by token JTI and user-purpose login rows before classifying an uncertain reply. For an enrolled account, try `/overview`, `/launch` or a unique machine admission through B before MFA, then complete one real WebAuthn ceremony through B and try the same action. A wrong-session, expired or replayed ceremony must not unlock the other login. A no-MFA account is a separate positive branch; its post-POST access is expected and must not be called a pending-MFA violation.

**Independent oracle.** The SMTP fixture records immutable recipient, Message-ID, accepted DATA bytes and accept/ACK phase; it establishes upstream acceptance, not inbox delivery. A read-only PostgreSQL observer counts exact token purposes/JTIs, verification rows and admitted VM request key/operation rows. The browser observes real redirect, session and LiveView/HTTP status. A unique admitted machine request can prove a forbidden domain effect without claiming physical guest success; if a guest is selected, a separately observed guest nonce can strengthen the positive journey. An HTTP 302 or flash alone is not proof of zero authority or zero effect. A lost SMTP ACK or POST response is **unknown** until the ledger and database are reconciled; duplicate SMTP acceptance is permitted under uncertainty.

**Source and intended contract.** `marshall/lib/marshall_web/automatic_magic_sign_in_live.ex:7-33` renders a CSRF-protected remembered POST without GET-side token action. `marshall/lib/marshall_web/router.ex:150-185` installs authentication and magic-link routes. `marshall/lib/marshall/accounts/auth_emails.ex:9-75` binds token to recipient and commits a per-recipient outbox/cooldown; `deliver_auth_email.ex:12-77,89-107,113-160` rechecks stored token, sends through SMTP and records terminal status. `marshall/lib/marshall/accounts/user.ex:144-199` wires sign-in and request actions. `magic_link_sign_in.ex:6-56` fences authoritative login issuance and revokes the strategy's post-commit token. `marshall/lib/marshall_web/controllers/auth_controller.ex:18-66` verifies that stored login and routes incomplete MFA to Security. `marshall/lib/marshall/accounts/security.ex:42-60,223-263` binds completion to a verification row and credential generation. `marshall/lib/marshall_web/live_user_auth.ex:23-103` checks stored login and MFA before protected LiveView work. ADR-0131 and ADR-0123 state the GET/POST and MFA separation; `marshall/test/marshall_web/magic_link_flow_test.exs:75-137` and `mfa_login_history_test.exs:17-70` are existing scoped tests.

**Value menu.** Existing/new account; MFA enabled/disabled; 0/1/2 GET previews; 1/2 concurrent POSTs; same/wrong browser session; valid/expired/revoked token; correct/wrong WebAuthn login JTI; SMTP accepted/ACK lost/accept unknown; POST committed/response lost; one/two Marshall processes. Use distinct synthetic emails and request IDs, never log link bytes.

**Focused topology and proof boundary.** Shared PostgreSQL, Marshall A/B, local SMTP acceptance recorder and real browser/HTTP workload. Actual HTTPS origin and WebAuthn RP must be consistent across replicas. This proves entry authority and committed control-plane effect only. A guest nonce variant needs real guest execution and private ingress; missing guest readiness does not make a pre-MFA refusal test pass.
