# Focus 03: Concurrency model

## Scope and evidence boundary

This is a fresh examination of Marshall, Lilly, Audi, Brady, Enrico, Galileo, Porsche, Ziggy, shared protocol/diagnostics/request-accounting libraries, Rust and guest helpers, browser terminal code, backup/updater runtime, and Nix service/test declarations. I read root guidance, the architecture overview and ADR index, relevant actor/ownership, database recovery and pool-lock decisions, application entrypoints, and targeted synchronization paths. Pattern searches covered the named component trees for GenServers, supervisors, ETS, tasks, native threads, locks, atomics, channels, and transaction locking. Targeted reads followed the strongest findings. This is not a line-by-line audit of every module or dependency.

No retired `antithesis/` artifact supplied analysis input. The repository has retirement changes staged over the stated baseline; linked historical reviews were treated as scoped reports, never current passing execution. Test files below establish test presence. Only an explicitly cited review supplies a historical execution claim. This pass ran no build, property, machine or hosted test and changes no SUT source.

## 1. Three different authorities serialize different work

Overalls has no single global application lock. Marshall uses PostgreSQL transactions to serialize durable domain decisions; provisioner actors use BEAM ownership to serialize local intent/journal reconciliation; native helpers use kernel locks and process lifetime to retain physical custody beyond BEAM or caller failure. Those are separate linearization points. A database commit authorizes work but does not prove a physical effect finished. A GenServer reply or native utility exit does not alone authorize capacity release.

Marshall's root supervisor is `:one_for_one` (`marshall/lib/marshall/application.ex:37`), serving independent Repo, authorization, Oban, PubSub, control/terminal task supervisors and Phoenix children. Operator mode disables Oban queues, plugins, leadership and staging and binds no serving listeners. `marshall/config/config.exs:50` configures Oban's Basic engine and PostgreSQL notifier, with default/provisioning concurrency 10 each, mail/maintenance 2 each, and certificate concurrency 1 when enabled. These are application queue limits, not an exactly-once promise. Concurrent replicas and replaying jobs still rely on database state and idempotency.

`Marshall.Compute.Ledger.transaction/2` (`compute/ledger.ex:20`) scopes audit attribution and after-commit callbacks in the current process dictionary. Its nested commit scopes discard rolled-back callbacks, and `lock!/2`/`lock_history!/2` use `FOR UPDATE` with the enclosing transaction lifetime (`:149`, `:162`). These process-local dictionaries do not synchronize replicas; PostgreSQL locks do.

Admission (`compute/admission.ex:46`) acquires a transaction advisory lock on owner plus idempotency key before the first VM exists, checks retained history, then atomically creates placement, reservations, address, operation, audit and dispatch job. Image availability uses `FOR SHARE` (`:176`). Global name claims serialize before placement locks (`:301`). `RelocationAdmission` sorts all candidate host IDs before locking hosts, then locks/rechecks VM authority (`compute/relocation_admission.ex:38`). `CloneCoordinator` serializes by source advisory lock, orders hosts and retained VM locks, and follows queued sequence rather than Oban arrival order (`compute/clone_coordinator.ex:23`). Host reports acquire the same host lock before applying complete ordered snapshots (`compute/host_reports.ex:23`). Good hosted targets are overlapping create/replay, report/admission, clone/cancel/relocate, image-disable/create, and user revocation after preliminary lookup. The observable invariant should use committed rows and physical receipts, not job execution counts.

## 2. Lilly single-flight execution meets persistent kernel custody

Lilly's root is `:rest_for_one` (`lilly/lib/lilly/application.ex:48`): execution views precede the configured control Link and Runtime; ingress and private services follow Runtime; image hashing is a later child so its own failure cannot restart earlier admission services. `Control.Runtime` acquires both fixed host ownership and the configured state-directory lock before opening the host-bound Store (`control/runtime.ex:148`, `:1066`). It starts a DynamicSupervisor for actors and monitors replacements. Shutdown kills outstanding sampling/exchange tasks and stops actors/transfer workers before releasing its lock ports (`:791`). Abrupt death is a distinct path that cannot depend on `terminate/2` running.

Each VM actor acquires its own journal lock and monitors the owning Runtime (`vm/actor.ex:50`). Before asynchronous work, it reloads durable command intent and persists the attempt epoch/generation. It refuses a second executor task while one is in flight (`:275`). A result and command change can overlap; the actor tracks the command used by that task and drives later intent through reconciliation. Boot probes are a separate task. This invites crash windows before attempt persistence, after attempt but before submission, after physical completion but before outcome persistence, and before outcome acknowledgement.

`Host.Lock` (`host/lock.ex:41`) starts a Rust port helper on a stable `owner.lock` inode and acknowledges acquisition only after an exact nonce echo. Definite contention alone is retried in a monotonic window of at most two seconds (`:13`); uncertain handshakes refuse immediately. Release sends the helper an orderly close frame and waits for actual exit, rather than equating BEAM port close with released flock (`:90`). `LockedCommand` runs bounded binary requests through that selected native owner (`host/locked_command.ex:9`). Nested ownership is recorded per BEAM process; `with_owner/2` selects the placement owner while other leases remain open (`host/lock.ex:142`). A worker must explicitly acquire/select its own ownership; spawning it does not transfer the process dictionary.

Native `host-lock` and `source-export` create process groups, act as child subreapers, install parent-death fences, retain lock descriptors across exec, and reap descendants before confirming release (`lilly/native/host-lock/src/lib.rs`; `native/source-export/src/lib.rs:415`). Thus caller/helper death and lock release are not interchangeable. An escaped descendant can retain custody while cleanup is uncertain. `launch-guard` blocks on a shared intent flock and only then reads and validates placement/epoch/generation/state before exec (`native/launch-guard/src/lib.rs:169`). Reading intent before waiting would admit stale authority. The shared descriptor crosses jailer exec until owned cgroup confinement supplies the next fence.

Existing native helper tests and `lilly/test/host/locked_command_test.exs:233` exercise caller/helper death, nested/shared leases, timeout/output retirement and paused-helper release. `nix/tests/machines/zfs-guest/actor-recovery.exs:303` holds real execution locks while persisted attempts contend. The 2026-10-03 native actor review reports a historical 671-second combined completion/contention pass; its scope does not prove every current daemon, updater or hosted composition.

The shared control client is itself a GenServer multiplexing bounded concurrent requests: default in-flight eight, negotiated maximum 256, monotonic request IDs, per-request timers, and correlated pending replies (`protocol/lib/overalls_protocol/control/client.ex:27`, `:128`, `:357`). Disconnect fails every pending request as unproven. Connection-opening workers are linked and monitored and must hand socket custody to the owner before publishing success (`:253`, `:289`). Race targets include timeout versus reply, old opening result versus replacement attempt, disconnect during admission, and caller cancellation before the transport result arrives.

## 3. Pool serialization is also a fairness boundary

`Host.Storage.locked/3` serializes snapshots, preparation, deletion and ownership mutations on one `.lilly-storage` lock per pool (`host/storage.ex:12`). Mutation acquisition defaults to one second; observations explicitly use zero wait and report contention as unavailable. Effects are never retried inside the ownership callback. `PoolSnapshot.held?/1` rejects using a snapshot after the exact lock is released (`host/pool_snapshot.ex:58`). Placement/readiness journal ordering is explicit: placement ownership first, then the journal audit lock, with no network wait or pool acquisition inside that journal lock (`vm/provisioning.ex:12`).

Runtime sampling and actor observations use `OverallsProtocol.Cadence`: one sample in flight, dropping intervening timer ticks so slow snapshots leave room for mutations (`control/runtime.ex:252`; `vm/actor.ex:500`). A source comment identifies earlier back-to-back sampling as starving clone source relaunches. ADR-0152 states whole-pool verification serialized four creates and documents the newer one-logical-snapshot preparation. It remains partial: native trace evidence exists, but a production four-way campaign is outstanding. This makes sustained create/delete/clone plus sampling/prewarming/refill a valuable progress workload. An oracle must distinguish definite contention from physical loss and ensure contention alone neither overwrites retained outcomes nor releases reservations.

## 4. Shared ETS views are atomic per row, not snapshots across keys

`OverallsProtocol.View` owns protected ETS tables with a unique writer claim per key, monitors writers, removes their rows on death, and assigns increasing versions (`protocol/lib/overalls_protocol/view.ex:119`). Readers access ETS directly. Publication inserts new index entries, atomically replaces the row, then removes obsolete entries; lookup verifies the current row still contains the term (`:95`, `:149`). Notifications contain a key hint and require rereading. Restart creates empty tables.

`Lilly.Execution.current/2` joins runtime-connected, durable intent, actor live-command equality and unexpired observation (`lilly/lib/lilly/execution.ex:126`). Those are separate ETS reads. The implementation enforces the described predicates at each read but does not provide one multi-key snapshot. Runtime disconnect, replacement intent and actor withdrawal can interleave with a successful lookup. This is a timing lead, not a demonstrated defect: later stream subscriptions, guard validation and physical fencing can close that interval. Properties should pin a precisely defined admission/forwarding boundary and exercise the composed path before asserting any forbidden stale use. `protocol/test/view_test.exs` has real-process generated owner/row/version histories; it does not by itself establish whole-stream revocation.

## 5. Gateways isolate lease renewal from blocked transport

Audi and Porsche use `:rest_for_one` roots so loss of proof registries restarts dependent listeners (`audi/lib/audi/application.ex:20`; `porsche/lib/porsche/application.ex:24`). Porsche bounds both connection children and command tasks at 4096; transient connection actors monitor one proven SSH connection and maintain one Marshall session (`porsche/lib/porsche/connection.ex:37`). Accepted domain work survives a connection close.

Audi's temporary `StreamGuard` monitors a dedicated socket owner and kills it on denial, changed binding, expiry or guard failure. An unlinked watchdog also monitors guard/owner and checks deadlines before queued renewals (`audi/lib/audi/authority/stream_guard.ex:125`). Renewal work runs outside the guard. Ziggy has 2048 task/lease ceilings, Finch pools of 256 connections times eight, and a serialized durable Spool (`ziggy/lib/ziggy/application.ex:28`). Its temporary lease targets the owner directly with the timer service and computes renewed remaining time from renewal start; a late success cannot revive an expired lease (`ziggy/lib/ziggy/lease.ex:45`). Galileo uses an independent lease process and monitored renewal/reader workers, checks lease state between upload/download steps, and disables HTTP/2 for its reviewed frontend-cancellation seam (`galileo/lib/galileo/upstream.ex:280`, `:411`; `application.ex:18`). Backpressure plus renewal stall, lost control connection and suspended guardian are especially useful composed tests.

Brady bounds each HTTP/HTTPS listener's monitored connection workers at 256 by default (`brady/lib/brady/listener.ex:40`). Its cache has an independent recovery supervisor; a single Store owner serializes budget reservations, publication and reader/writer leases, monitors callers, and cleans leases on death (`brady/lib/brady/cache/store.ex:159`, `:371`). Cache failure need not stop proxy listeners. Enrico couples Manager and capped task supervision under `:one_for_all`, admitting eight refreshes and one active attempt per repository (`enrico/lib/enrico/refresh_supervisor.ex:19`; `manager.ex:66`). Generation references exclude stale completions. Eight inherited native admission flocks independently cap Git utilities across BEAM replacement (`enrico/native/git-owner/src/main.rs:100`). Results may precede task exit; process-held slots still bound physical overlap. Native history tests include helper death, escaped descendants and saturated admission.

## 6. Rust, browser and operational concurrency

Terminald uses a thread per accepted vsock connection plus per-session pump/viewer threads. `session.rs` protects sessions, creation receipts, session state, viewer queues and drain signalling with distinct Mutex/Condvar structures; ring/viewer budgets use atomic reservations (`nix/packages/terminald/src/session.rs:104`, `:842`). Creation-retry/cancellation holds the creation map while consulting sessions; pumping acquires session then viewer queues, and draining coordinates separately. Retirement drops ring backing before returning quota and removes the session only after PTY cleanup (`:748`). Generated budget, mixed-growth, neighbor-progress and retired-ring tests exist. A concurrency workload should combine replayed creates, cancellation, session EOF, viewer saturation and neighbor output; no deadlock is claimed from the reviewed lock excerpts.

The editor broker uses a global UID-to-lock map briefly, then holds only the selected account mutex during bounded worker ensure/probe/start (`nix/packages/vscode-web-broker/src/main.rs:580`). Atomic connection admission and per-account locking permit distinct accounts to progress concurrently; broker restart relies on systemd unit metadata/socket custody rather than retained in-memory mutexes. Browser terminal code is event-loop asynchronous: delayed ticket replies check current selection and LiveView connectivity; attachment waits for pending output writes, preserves replay cursors, and uses bounded reconnect timers (`marshall/assets/js/terminals/tickets.js:20`; `terminals.js:414`, `:536`, `:1080`). Test delivery order matters as much as native thread order.

Durable request accounting serializes producer admission/completion/death in a GenServer with 4096 pending tickets (`elixir/request_accounting/lib/overalls/request_accounting/producer/server.ex:8`). Rust recorder intake is single-threaded with 250ms read/write limits and independent once-per-second reconciliation (`nix/modules/otel-guest/receiver/src/request_recorder.rs:560`); boot/start identity and pidfds distinguish death from uncertainty. Trace custody instead shares an `Arc<Mutex<Store>>` between intake and exporter, releasing that mutex before network I/O (`elixir/diagnostics/native/spool/src/main.rs:324`). Ordinary guest telemetry uses capped threads, atomic active counts and a mutex-protected rate limit (`nix/modules/otel-guest/receiver/src/main.rs:242`). Underclass's repository patch and SLO adapter add a mutex-protected durable connection, atomic fence and background reconciliation; upstream runtime code is fetched, limiting repository-only visibility.

Backups serialize all operations with one host owner flock; only status publication/heartbeat is shared between Python threads under `status_lock` (`nix/modules/backups/runtime.py:31`, `:277`). Updater execution/cleanup use the same update flock. Migration uses a fixed bounded systemd unit plus PostgreSQL session advisory migration locking, avoiding duplicate surviving migrators (`nix/modules/auto-update/runtime.py:554`; `marshall/config/config.exs:43`). Socket activators stop before consumer services and restart after them. Guest Inception helpers similarly use bootstrap, ingress, job and worker flocks; proof serving has a four-slot bounded semaphore and 500ms deadline (`nix/packages/guest/inception/observations.py:331`). Cross-release tests must observe actual children, locks, sockets and generation identities, not just service exit status.

## Assumptions, open questions and feasible environments

Hosted Linux containers can cover real BEAM scheduling, PostgreSQL contention, control connections, Unix peer ownership, threaded helpers, browser ordering and ordinary kernel flocks. Emulated executors can drive journal and cross-service histories but cannot establish KVM, jailer/cgroup fencing, real ZFS pool locks, mount namespaces or guest socket custody. Native NixOS/Ubuntu machines with ZFS and Firecracker remain required for those boundaries. Existing machine fixtures provide starting points, not hosted compatibility evidence.

Open questions are whether hosted infrastructure permits required kernel features and deterministic observation of inherited-descendant locks; whether the exact current tree passes the existing concurrency suites; whether composed execution-view reads can admit a stale grant before subsequent fences; and whether sustained mutations, samplers, templates and standbys meet useful fairness bounds. Test those questions before selecting claimed invariants. Repository evidence shows carefully designed serialization and refusal contracts, but does not establish absence of all races or a universal progress bound.
