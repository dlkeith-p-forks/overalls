# Existing test strategy

Overalls already has substantial unit, generated-history, distributed-database, browser, Linux-native-helper and NixOS machine coverage. The opportunity for a fresh Antithesis workload is the composition of real authorities, retained state, reconnecting clients and long-lived effects under varied fault timing. Repeating codec round trips or treating a fake VM launch as native execution would add little evidence. The repository explicitly requires that distinction: `AGENTS.md:50–52`, `CONTRACTS:20–25`, `lilly/test/CONTRACTS:1–10` and `nix/verification/tests/CONTRACTS:1–8` separate test existence and successful execution from isolation, multi-host availability and production throughput.

This pass inspected the root and component guidance, architecture overview, assurance/machine ADRs, current test catalogs, selected test implementations, local and ancestor contracts, and repository execution reviews. It did not execute suites or read the old Antithesis directory, historical scratchbook, outside-repository logs, issue trackers or public documentation. “Recorded pass” below means a repository document records execution at its specified revision; it is not a new run against this baseline. Research-only output outside the repository changes no architecture or HLDD behavior.

## 1. Ordinary gates and distributed evidence

A source inventory found 320 files under Marshall test, 136 Lilly, 48 Audi, 27 Brady, 6 Enrico, 12 Galileo, 17 Porsche, 20 Ziggy and 67 protocol. A deliberately coarse search for ExUnitProperties, StreamData, `check all` or property declarations matched respectively 145, 73, 33, 18, 3, 7, 12, 11 and 50 files. These are file counts, including support files, not test counts, coverage percentages or execution results. They establish that generated testing is already widespread.

Marshall's ordinary `ExUnit.start` excludes `distributed`, `host` and `capacity`, while its `precommit` explicitly includes distributed tests and runs compiler, contracts, logging, browser-state checks and forced Dialyzer (`marshall/test/test_helper.exs:1–3`; `marshall/mix.exs:150–163`). A casual `mix test` therefore gives weaker evidence than the documented gate, and even precommit does not establish host/capacity acceptance. Lilly precommit similarly forces Dialyzer; protocol has a compiler/test/Dialyzer gate (`lilly/mix.exs:52–61`; `protocol/mix.exs:18–26`). Marshall's test-only dependencies on Lilly, Porsche and Audi support real application-boundary tests without coupling production releases (`marshall/mix.exs:53–55`; `marshall/CONTRACTS:6–10`).

The distributed tests are stronger than simultaneous tasks in one process. Admission starts three distinct BEAM peers with independent Repo pools against committed PostgreSQL; the coordinating parent is explicitly excluded from the count (`marshall/test/marshall/compute/distributed_admission_test.exs:43–68`). Fixture setup snapshots durable inventories and teardown restores only owned rows (`:21–38`). This is useful admission/authority race evidence, but all peers share the test machine and database. It neither proves independent host survival nor explores every network/kernel failure. A fresh workload should retain real PostgreSQL transactions and multiple Marshall instances, exercise concurrent admission, relocation cancellation, revocation and retry, and validate committed inventories independently of client receipts.

## 2. Component evidence and its substitutions

**Marshall and protocol.** Marshall has SQL-backed domain, policy, credential, lifecycle and LiveView tests plus distributed histories. Protocol tests cover closed wire versions, identities, budgets, terminal framing, editor grants, transfer descriptors and transport state. For example, execution decoding refuses unsupported v1–v3 control documents, missing placement/epoch and incoherent readiness (`protocol/test/execution_test.exs:43–85`). These tests verify parsing and application decisions; successful encoding is not evidence of external validation (`protocol/CONTRACTS:23–26`). Cross-consumer tests are necessary because a correct decoder alone cannot establish caller correlation, stream lifetime or durable receipt custody.

**Lilly.** Ordinary tests intentionally run without root/KVM. Actor histories exercise real Store/Journal/Actor code with a durable fake executor: replay/generation advancement, a persisted attempted marker, actor death before outcome recording and adoption after completion (`lilly/test/vm/antithesis_actor_property_test.exs:18–77`, `:84–133`, `:142–204`). The separate fake-executor property checks command-caused observations and at-most-once attempt accounting (`lilly/test/vm/fake_executor_property_test.exs:7–105`). Those retained unit tests are production-state-machine evidence, not an existing harness to reuse. Their synthetic physical observations cannot prove jail, ZFS, network or VMM behavior. Antithesis emulation must expose the same uncertainty windows and independently model accepted commands; otherwise the oracle and substitute executor can agree while real execution is wrong.

**Audi.** Generated lease tests check that network delay consumes grant lifetime, late renewal cannot revive expiry and binding/reply order stays fenced (`audi/test/authority_lease_test.exs:7–42`). DNS, SSH, HTTP, WebSocket, editor, TLS and PKI suites add boundary coverage. The repository records actual nested-guest fleet journeys for DNS, HTTPS, SSH, sharing, revocation, gateway restart and relocation (`docs/services/audi.md:14–50`). Those records preserve old certificate/wildcard revisions and bounded scope. Important new schedules cross DNS publication, gateway assets/readiness, current Marshall authorization and Lilly physical execution; DNS success alone must never authorize traffic.

**Brady.** Cache-history properties use real files and owners to check exact publication bytes, privacy bypass and reader ownership through pressure, close and death (`brady/test/brady/cache_history_test.exs:102–186`). The review explains the independent expected-body model and records a deliberately broken Authorization normalization being caught, followed by restored passing gates (`docs/architecture/reviews/2026-09-26-cache-history-verification.md:47–73`, `:91–102`). Native checks use kernel interception/TLS and optional ZFS disks (`nix/verification/tests/machines/brady-network/default.nix:17–24`); prior native/fleet runs are revision-scoped (`cache-history-verification.md:35–43`). The fresh opportunity is response streaming, publication custody, cache pressure and owner replacement occurring together, rather than another static policy matrix.

**Enrico.** Small file count does not mean mock-only coverage. Manager properties invoke the real `enrico-git-owner` native helper for occupied-writer custody, while other restart histories substitute a controlled Git executable (`enrico/test/manager_history_property_test.exs:13–56`, `:72–85`). Packaged machine tests use a verified HTTPS Git fixture and check published-mirror preservation, interrupted refresh accounting and no replay (`nix/verification/tests/machines/enrico-service/default.nix:104–113`). Native helper histories exist at `enrico/native/git-owner/tests/histories.rs`. Local Git/origin fixtures are appropriate for timing exploration, but public GitHub/provider availability and a full Marshall-browser mirror journey require their own evidence.

**Galileo.** Component streaming/lease tests and the packaged Audi-to-Galileo service suite include exact upload bytes, stalls, binding changes and controlled origin/control TLS. Its local contract expressly excludes real Lilly, Marshall, attachment, relocation and Firecracker acceptance (`nix/verification/tests/machines/galileo-service/default.nix:161–166`). Separate recorded fleet acceptance includes three Marshall releases, two Lilly hosts, real guests, attachment withdrawal, peer provenance, relocation and all-Marshall outage (`docs/services/galileo.md:97–118`). Local fixture behavior is a useful oracle for upstream ordering but cannot substitute for real renewable authority or single-use peer-token consumption across replicas.

**Porsche.** Native OpenSSH channel tests exercise exec, stdout/stderr, approval, retained sessions, input fragmentation, listener death and disabled forwarding (`porsche/test/ssh_channel_test.exs:96–244`, `:301–404`). The service machine suite proves packaged startup, custody and port separation but explicitly has no Marshall/domain/guest execution (`nix/verification/tests/machines/porsche-service/default.nix:103–106`). Full fleet and team-SSH compositions add those different authorities. New exploration should mix connection replacement, retained request replay, pending response retirement and credential revocation; a successful SSH JSON result is insufficient without committed Marshall and physical outcome checks.

**Ziggy.** Reporter histories check exact retained receipts and healthy-neighbor drain (`ziggy/test/reporter_history_test.exs:22–23`), while spool, leases, provider selection, usage and stream suites cover component logic. The machine suite uses real packaged Ziggy, SOPS, verified provider TLS and disk accounting, but synthetic control authority (`nix/verification/tests/machines/ziggy-service/default.nix:94–99`). Its verification ledger records implementation-time gates and specifically leaves complete two-host Firecracker request/relocation/lifecycle, 1,000 real streams per host for fifteen minutes, and complete-chain rotation/spool/update failure work open (`docs/services/ziggy.md:90–126`). These old ledger counts are not this baseline's results. Preserve unknown usage and no automatic inference replay while faulting both request and completion paths.

## 3. Machine, browser, terminal and guest-service layers

Checks are explicitly exported; adding a test file alone does not schedule it (`nix/verification/tests/catalog.nix:33–44`; `nix/verification/tests/README.md:26–29`). Fleet composition names three Marshall nodes, two Lilly nodes and separate PostgreSQL; it requires nested KVM and uses 3,600-second or relocation 10,800-second global bounds (`nix/verification/tests/machines/fleet/default.nix:1287–1308`). Recorded historic full-fleet results include real packet isolation, six-guest admission, database/machine outages, VM survival and retained storage (`ADR-0033:261–286`). ADR-0033 is superseded by ADR-0043, so its rationale and historical test evidence should not be mistaken for the current deployment status (`docs/architecture/decisions/0033-nixos-machine-verification.md:5–15`).

Hegel integration is explicit in only four current machine `default.nix` suites: underclass-service, secret-custody, zfs-transfer and agent-cli. The migration review records three real KVM passes, while agent-cli failed an earlier linear assertion before its generated additions ran (`docs/architecture/reviews/2026-09-26-hegel-machine-property-testing.md:39–73`). Other machine checks do contain Hypothesis histories: runtime-readiness restarts, submission recovery, backup cleanup, recorder reply loss and updater custody. Their menus remain bounded; for example runtime-readiness draws two restart counts per host and distinguishes VMM survival during database outage (`nix/verification/tests/machines/fleet/scenarios/runtime-readiness.py:7–45`). Generated test presence is therefore broad but whole-fleet arbitrary-order exploration remains incomplete.

Browser evidence includes typed Playwright artifacts for ordinary account/Teams/MFA/control-room/creation and fleet journeys. These separate processes receive their own pinned type checks; composed-driver typing cannot see them (`nix/verification/tests/README.md:31–62`). Browser/controller tests alone cannot establish TLS, WebAuthn device behavior or live guest effects. Native terminald tests run offline Cargo tests and Clippy in an explicit Nix build phase despite `doCheck = false` (`nix/domains/artifacts/infrastructure/terminald-checks.nix:14–23`). Independent ring/frame properties compare exact bytes but expressly exclude authenticated vsock, PTY backpressure and browser delivery (`2026-10-03-terminald-byte-histories.md:17–30`). Existing terminal fleet journeys should remain separate from those pure budget/codec oracles.

Editor evidence particularly illustrates revision risk. The final Code OSS package/broker standalone native run is recorded successful with UID custody, real Rust/Elixir responses and worker recovery, but has a synthetic authorizer/TLS relay; earlier complete NixOS/Ubuntu fleet passes used an older startup release (`docs/architecture/reviews/2026-10-10-browser-editor.md:1554–1586`). The subsequent stopped-only-relocation merge explicitly lacks a complete merged rerun (`:1597–1622`). Multi-writer/stale-account, gallery signature, gateway readiness/expiry, idle/retirement and recurring-production histories remain distinct (`marshall/priv/hldd/19-coverage.md:87–107`, `:129–147`). Guest NixOS/Ubuntu, private DNS/TLS, SSH trust, agent executor/updater, Inception child services and source2 delivery must retain actual image and service capabilities when testing those journeys; endpoint fixtures cannot establish native guest identity or execution fencing.

Backups combine schema/evaluation tests, generated cleanup histories and actual ZFS/Restic/PostgreSQL/MinIO machines (`nix/verification/tests/machines/backups/default.nix:1–35`, `:75–98`). Native cleanup checks independent snapshot GUID/content preservation and refuses foreign or uncertain proofs (`nix/verification/tests/machines/backup-cleanup/native_cleanup.py:100–145`). Publishing recovery histories exercise packaged persisted journals, not producer death at an upload boundary; recorded passes leave complete upload/manifest durability, capture/retention composition, concurrent cleanup, namespace recovery and physical loss open (`2026-10-03-backup-publication-recovery.md:14–51`). Nix itself has core/native compact-output, daemon, remote protocol and interruption checks (`nix/verification/tests/README.md:113–116`), but native storage performance, live providers and independent physical failure domains remain separate.

## 4. Hosted versus native feasibility and strongest gaps

Repository evidence supports ordinary-container exploration of actual BEAM releases, PostgreSQL, shared protocol clients, HTTP/SSH/Git/provider fixtures, caches/spools and many Linux process helpers. A control-only Lilly or explicit executor substitute can exercise actor/journal uncertainty, but must label physical outcomes emulated. The real ownership path requires root, PID1 systemd, enrolled x86-64 identity, the exact Lilly cgroup, native KVM probe and network setup (`lilly/lib/lilly/host/ownership.ex:9–27`, `:56–64`). Native NixOS suites additionally need kernel ZFS, devices, nftables, namespaces and actual nested Firecracker. Unaccelerated QEMU or a mocked KVM file would not satisfy these gates. No repository evidence establishes which of these capabilities a hosted Antithesis environment supports; capability proof is an open setup prerequisite, not permission to weaken production checks.

The strongest uncovered portfolio targets are: concurrent authority/intent/physical-outcome composition across all service clients; stale and uncertain renewal/reconnect histories with real Marshall/PostgreSQL; actual process-owner death while helpers retain descendants or output; incomplete backup publication and cleanup composition; and current combined guest/editor/identity/relocation revision acceptance. Keep native Hegel/NixOS tests as complementary evidence when hosted execution cannot preserve those boundaries. Do not imply a hosted synthetic launch proves VM isolation, independent power-loss resilience, real provider acceptance, sustained capacity or final merged-source readiness.

## Open questions

- Which real host primitives are available in the target hosted environment, including nested KVM, ZFS and privileged network/cgroup setup? Repository-only scope cannot answer this.
- Which current merged-source NixOS/Ubuntu fleet and final editor-release checks have newly recorded execution after this baseline? Existing reviews intentionally keep older revisions separate.
- Can workload observers distinguish accepted intent, retained receipt, completed external effect and acknowledged accounting without relying on a substituted executor's own state?
- Which generated native suites complete initialization on the chosen environment? The historical agent-cli failure shows this must be checked before crediting property execution.
