# brady-flow-attribution-requires-current-incarnation

**Type/priority/status:** Safety, P0; proposed, unimplemented, unexecuted. Primary `Always(condition, "Brady resolves flow ownership only for the current labeled execution incarnation")`. `Always` checks each **new resolution** against independent physical/current-intent evidence at the resolution boundary. A supplementary `Reachable(old_flow_unresolved_after_reuse, "Old guest flow remains unresolved after address reuse")` guides the rare stale-flow branch. A request with unresolved attribution may still be safely proxied; the assertion is about identity, not egress denial.

**Property:** At initial lookup, the owner, placement, epoch and generation attached to a Brady connection must derive from the accepted socket's complete original kernel tuple and a label matching one then-current, physically verified execution. An old labeled flow retained across rule replacement or guest address reuse cannot be attributed to the new occupant. Brady's one-time result on an already accepted socket is not retroactively rewritten after a later execution change.

**Primary source:** `lilly/lib/lilly/network/flow_label.ex:7-29,34-51` hashes host/placement/epoch/generation and labels only a new unconfirmed original TCP SYN from the claimed TAP. `lilly/lib/lilly/network/flow_lookup.ex:8-17,20-44` requires exact source and destination endpoints. `lilly/lib/lilly/network/attribution.ex:5-29,40-53` rereads kernel label and execution row around owner resolution. `brady/lib/brady/connection.ex:5-18,51-64` takes both addresses from the accepted socket and snapshots one result. ADR-0069's attribution section specifies the physical join; a label or owner field alone is insufficient.

**Independent oracle and action/fault recipe:** Run a native Firecracker guest A with authenticated owner A. Open and hold a TCP connection through transparent Brady to a controlled origin, recording its exact four-tuple, conntrack label, physical boot ID and owner from the authoritative VM record into a workload-owned ledger. Stop/revoke A, retire its execution, reuse the address for guest B with owner B and a distinct placement/epoch, and restart Lilly/Brady near the cutover. Hold the old accepted socket across rule changes when possible; open a fresh B socket. Correlate closed Brady attribution events by a harness-only socket/flow ID with the independent tuple, label and physical intent **at each connection's initial lookup**. Every new `resolved` row must match the then-current incarnation; an old flow's frozen A result may remain A on its already accepted socket, but must never become B. A new lookup for an orphaned old flow should be unresolved. The B fresh-flow positive control should eventually resolve B. Never infer identity from guest headers, IP alone or Brady's own claimed owner.

**Value menu:** same/different owner; same reused guest IP but new placement/epoch/generation; old socket open/closed; conntrack retained/expired; Lilly owner cache fresh/expired; restart Brady before/after Lilly; exact tuple collision absent/present. Use synthetic owners and a private, redacted oracle ledger.

**Topology/proof limit:** `storage-router` can test exact tuple labels and unresolved failure using real conntrack, but its veth peer is not a current Firecracker execution source. The full current-physical-owner statement needs native KVM and actual authoritative VM records. The existing catalog covers stale ingress streams and guest UID identity; neither covers Brady connection ownership.

**Open questions:** How can the harness retain and identify one accepted Brady socket through address reuse without exposing the URL or guest bytes? `(partial: accepted tuple is available in Connection.run, but no test-only socket ID exists)`; can native fixture schedule address reassignment while retaining an old conntrack entry? `(partial: ADR-0069 describes scenario and fleet Brady source has old-flow probes, but current composed execution is unverified)`.
