# lyra-guest-update-fences-executor-handoff

**Type and priority.** Safety, P1, high confidence in the conditional source contract. Planned primary `Always` SDK message: **"Lyra guest update never runs unverified or overlapping executors"**. On a staged guest update, no candidate executable may run unless its staged bytes still match the fetched target digest, the prior executor has exited after the graceful stop request, and the candidate's managed executable has the verified identity. If candidate spawn fails or registration returns false, the previous executable is restored before restarting. This checks every relevant handoff and recovery observation; `Always` matches a must-hold safety claim. Registration/status I/O errors propagate, and a registration-successful candidate has no semantic rollback guarantee. Supplementary `Reachable` message **"Lyra guest update restored prior executable after failed registration"** identifies the useful failure branch. The [fresh scan](../existing-assertions.md) shows this SDK instrumentation missing.

**Source and distinction.** `lyra/src/update.rs:235-319` validates manifest target/path/size and SHA-256 before fsynced pending publication; `:331-360` rechecks staged digest, saves the prior executable and renames pending to managed; `:420-449` waits up to 90 seconds for the candidate's exact digest registration, then restores the previous binary on a false result; `:459-516` asks the old executor to stop, waits up to 60 seconds and activates only after actual exit. `lyra/CONTRACTS` carries guest execution and closed diagnostics. ADR-0104 describes this guest seed contract. Fleet host `nix/modules/auto-update/runtime.py` changes Nix closures/systemd roles and uses `lastHealthy`; its existing catalog rows cannot establish Lyra's managed binary inode or guest command handoff.

**Workload and independent oracle.** Boot a real pinned guest image with immutable seed, managed executable and private update endpoint. Publish a bounded valid target and variants with wrong digest/size/target; run a tagged command whose physical file effect can be read back from the guest disk. Hold the command at a controlled side-effect barrier while staging; release it, then observe old executor PID/boot identity, candidate PID and `/run/overalls-agent/ready` digest plus independently hashed managed/previous executable bytes. Fault the candidate before registration and restart the seed around previous-link, pending rename and status publication. The oracle checks no overlapping command execution, no candidate effect from invalid bytes, and restoration before new work after false registration. Command arguments, outputs, tokens and update payload bytes never enter diagnostics or assertion metadata; only opaque IDs/digests and effect counts may be reported.

**Value families and guidance.** Valid/corrupt/missing target; exact/wrong 64-character digest; artifact size at/below/above the configured maximum; old command idle/active; exit just before/at/after 60-second drain; candidate ready exact/wrong/missing at 90 seconds; interruption before/after prior hard link, pending rename, status write, registration and rollback; one/repeated seed restart. Place optional branch markers at digest recheck, old-child exit, managed rename and failed registration, not on mere updater invocation. A file-only Rust unit test can prove digest/rename logic but cannot prove live guest process exclusivity. TCG can exercise real guest process/storage and private endpoint; native KVM remains needed for the deployed guest image and boot chain. Current source and native test presence are not a recorded current run.

**Open question.** Can a source-built real guest fixture control candidate registration and stop/interrupt the seed at each durable handoff without replacing the real supervisor or guest executable? Investigate the existing `lyra/tests/guest_supervisor.rs` and native guest CLI recovery fixture before implementing the Antithesis workload. This is an implementability gap, not a confirmed defect.
