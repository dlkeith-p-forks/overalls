# galileo-accounting-delay-does-not-renew-old-grant

P0; medium-high confidence; safety. Proposed `Always` message **"Galileo accounting delay cannot start an upstream effect on an aged grant"**. Antithesis instrumentation is **missing** per [fresh scan](../existing-assertions.md). This is a test target and source-grounded timing hypothesis, not a reported or reproduced defect.

Source: `marshall/lib/marshall/galileo/authorizations.ex:11,21-52` grants a fixed 2,000 ms relative TTL after transactional execution/attachment checks and `:61-72` makes renewal repeat them. `protocol/lib/overalls_protocol/integration.ex:149-176` accepts only 500–5,000 ms TTLs. `galileo/lib/galileo/http.ex:98-133` obtains authorization, then synchronously calls `Overalls.RequestAccounting.Producer.admit/2` before invoking `Upstream.stream/2`. That call can wait up to 5,000 ms (`elixir/request_accounting/lib/overalls/request_accounting/producer.ex:49-64`). `galileo/lib/galileo/upstream.ex:71-85,411-428` starts a fresh deadline from the full TTL only inside `stream/2`, after the accounting wait. ADR-0140/0153/0158 security and lease rationale should be read with these callsites; the code ordering creates the question.

History: use a current real VM/integration binding and a controlled HTTPS upstream with a one-use side-effect counter. Let Marshall authorize, then block Galileo's recorder/producer admit long enough to exceed the 2,000 ms grant. Revoke the integration or VM attachment during the wait, release the recorder and observe whether Galileo connects, sends headers or pulls request bytes before any successful fresh renewal. Repeat with admission returning `:unrecorded`, with a quick accounting success, and with revocation just before/after the initial grant. Maintain a live authorization control case to prove the upstream is reachable. A blocked recorder is an observation-system fault, not an upstream fault.

Independent oracle: capture monotonic time at grant return and at first upstream socket accept, first header/credential read and first body byte using the controlled upstream, plus Marshall's committed revocation and renewal response. Count any upstream effect after the original grant expires and before successful renewal. Final HTTP status and accounting outcome alone cannot prove absence of an effect. If the design instead defines TTL only from `Upstream.stream/2`, record that explicit authority decision; no source currently carries a grant timestamp through the accounting wait.

SUT guidance: `Reachable` **"Galileo accounting admission outlasted initial authorization TTL"** at the handoff to `stream/2` is a high-value semantic branch; proposed `AlwaysOrUnreachable` **"Galileo upstream start had fresh authority after accounting wait"** at the optional connect/send path checks the same authorization age. The workload `Always` uses upstream effect and renewal witnesses. Do not expose tokens, headers or request bodies in assertion metadata.

Values: recorder admission 0/499/500/1,999/2,000/2,001/5,000 ms; grant TTL 500/2,000/5,000 ms where protocol permits; revocation before grant/during admit/after renewal; recorder success/gap/timeout; upstream accept before/after expiry; body absent/present. Production's fixed grant is 2,000 ms; other TTLs are protocol-bound tests. Real services and controlled upstream suffice; no native guest isolation claim. The fault controller must avoid assuming an exact wall-clock scheduling bound.

Open questions: Does a controlled end-to-end request produce an upstream effect after accounting delay exceeds the original 2,000-ms grant without a successful renewal? `(partial: source proves the full TTL restarts after accounting; effect and intended start point need a timed controlled-upstream probe)`
