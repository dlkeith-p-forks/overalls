# brady-sensitive-exchanges-never-reuse-shared-cache

**Type/priority/status:** Safety, P0; proposed, unimplemented, unexecuted. Primary `Always(condition, "Credentialed requests never reuse and private responses never enter Brady shared cache")`. `Always` checks each sensitive request's actual body provenance and each private response's storage effect; a single cross-guest credentialed hit or private publication is decisive. `Sometimes(public_anonymous_hit, "Anonymous public variant can reuse a complete Brady object")` is a positive control, subordinate to `brady-cache-complete-publication`.

**Property:** Credentialed, cookie-bearing, signed-query or non-range conditional requests cannot read or publish a shared object, even when the origin returns a public-looking response and another guest previously warmed the same path. Responses marked private/no-store cannot be published. `Range`/`If-Range` may read a fresh complete public object under the explicit read-only exception and must be assessed separately. A later origin policy change cannot retroactively invalidate an already fresh, formerly public object; exercise response-policy refusal on an unwarmed variant. Public anonymous variants stay separated by exact authority and supported Vary fields. This candidate addresses privacy/eligibility, not completeness, quota or pressure.

**Primary source:** `brady/CONTRACTS:7-14` requires public-only anonymous complete caching and streaming under failure. `brady/lib/brady/cache/policy.ex:12-33,35-68,76-86` rejects credential/cookie/query/conditional requests and sensitive response headers, requires public freshness and keys exact authority/variant. `brady/lib/brady/proxy.ex:84-106,109-135,190-255` validates authority before lookup and handles storage attempts after forwarding. `nix/tests/machines/brady-network/storage.py:49-61` exercises synthetic secret bypass in a ZFS fixture; this is source/test presence, not current Antithesis or native result.

**Independent oracle and action/fault recipe:** Give a fixture origin deterministic response bodies keyed to a synthetic requester/nonce and an append-only request ledger. Warm a cacheable public anonymous path as guest A, then issue guest B requests with Authorization, Cookie, Proxy-Authorization, signed query and non-range validators to the same path/host where legal. On an unwarmed variant, return `private`, `no-store` or `Set-Cookie` and repeat it. Reissue each after origin content changes and across Brady/cache restart. The origin ledger must show a new upstream request for every request-sensitive exchange, guest bytes must equal that request's response nonce, and the root-owned cache inventory must contain no private-response body/hash. For public Vary, compare missing/empty/different values and verify each selected body against origin ledger. During a withheld or crashed origin, a request-sensitive exchange must fail or receive the correctly fresh upstream result, never stale A bytes. Keep nonces/headers out of SUT diagnostics; the harness ledger is private synthetic evidence.

**Value menu:** two guest owners; HTTP/HTTPS; empty/credentialed/signed-query; response public/private/no-store/Set-Cookie; Vary missing/empty/changed; warm/cold cache; restart midway; origin held/available; non-range validator; `Range`/`If-Range` public complete-object exception as a separate branch. Use small deterministic objects first; cache size behavior is another property.

**Topology/proof limit:** `storage-router` can prove real Brady policy plus ZFS object custody under TCG. A simpler Brady+origin hosted template can prove application-level reuse but not transparent interception or ZFS. Full guest-to-cache behavior requires native Firecracker. Do not claim a secret leak from merely inspecting a unit test or a policy source branch.

**Open questions:** What harness-private cache inventory API can associate an object with a synthetic response hash without reading production-like payloads? `(partial: store has object files and existing storage fixture counts bodies, but no per-origin hash oracle is assembled)`; how will the fixture force the same original destination with two distinguishable guests under TCG? `(partial: topology specifies veth clients, but no composed template exists)`.
