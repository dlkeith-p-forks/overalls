# Inner private trust and enrollment source review

Date: 2026-10-13. Scope: the TCG inner Lilly host's private PKI, measured-host satellite issuance, private Audi/Ziggy/Galileo configuration, guest trust receipt, and admission readiness. This is source inspection, not a VM boot, image build, native Firecracker/KVM run, or remote Antithesis result.

## Findings and disposition

- **Private image selection, repaired during review.** The private host and guest image existed in `antithesis/nix/images.nix`, but the selectable `private-host-vmm` context initially lacked the closure allowlist, staging allowlist, Docker stage and Compose selection. Selecting the inner-private Compose overlay would therefore still start the ordinary host image, leaving its private services and boot-time guest trust absent. The current shared-worktree diff adds the context to `antithesis/nix/closures.nix` and `antithesis/build/prepare-contexts.sh`, adds the Docker stage, and selects that stage in `antithesis/config/compose.inner-private.yaml`. Source wiring is now coherent; its built image and live behavior remain to be verified by the integration owner.
- **No confirmed outstanding identity-binding or guest-trust defect in the inspected path.** `inner-satellite-enroll.sh` checks the Marshall-issued measured-host credential, the separate host fixture, distinct outer/inner host IDs, and each role's verified host ID before publication. `private_bootstrap.py` retains a root-owned CA/key manifest, checks leaf hostnames and key pairs, and copies separate host-bound Ziggy/Galileo tokens into role-owned runtime directories. `GuestTrustReceipt` binds the persisted receipt to placement, epoch, generation, boot challenge, root digest and guest boot ID. `GuestExecutor` requires current process proof before and after delivery, then guest readiness with the same boot ID; `GuestChannels` requires that receipt for terminal dial options.
- **Private connector path is intentional.** `private_bootstrap.py` configures Audi at `/run/lilly-ingress/private.sock`. `Lilly.Application.private_children/1` derives that same path from the configured ingress directory when private services are enabled. The ordinary `/run/lilly-ingress/audi.sock` listener is disabled by `audi_ingress: false`. An earlier apparent mismatch was retracted after tracing both constructors.

## Readiness and evidence boundary

`Lilly.Private.Readiness` requires Ziggy's host-ID-bearing live health reply and Audi's live status reply. Audi's private status checks its DNS listener and a verified TLS handshake for `llm.internal`; it does not prove an authorized guest-to-Audi-to-Ziggy/Galileo transaction. The private server checks Audi's local UID and uses the current Lilly execution view for binding. The outer `lilly-host-vmm` health check requires a recent inner Control connection, while the physical observation separately reports `execution_ready`. Guest, Audi, terminal, and integration acceptance must therefore be shown by their actual transaction or independent oracle, not inferred from container health or TLS alone.

The private host is a QEMU TCG harness variant. It can establish source-built protocol, trust and software-emulated boot behavior when run; it cannot establish native Firecracker/KVM isolation or production fleet acceptance. Relevant accepted decisions: ADR-0017 (host ownership and readiness), ADR-0025 (protected enrollment), ADR-0047 (Audi ingress), and ADR-0113 (boot-bound guest trust). This review preserves those decisions and changes no production architecture. No VM, image build, remote run, or full project gate was run for this source review; `cc-check` was unavailable in the review shell, so contract obligations were inspected manually.
