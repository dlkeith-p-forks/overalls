# Audi-mediated guest SSH review

- Date: 2026-09-22
- Decision: [ADR-0093](../decisions/0093-audi-mediated-guest-ssh.md)
- Status: implemented and live-accepted

## Scope and boundary assessment

This is a substantive access and isolation change. It adds a root SSH endpoint
inside ordinary guests but does not create a new public route: Audi's existing
VM-bound authorization, profile destination and port-22 fence remain the outer
boundary. Porsche contributes identity only by pinning its already authenticated
session key. Galileo is unchanged.

The design separates three authorities: Porsche authenticates the creation
request, the immutable provision snapshot bootstraps one guest key, and Audi
authorizes every later network connection. Guest disk retention, not mutable
Marshall key state, controls the inner authorized key and host identity.

## Security and recovery findings

- The protocol rejects key material on every non-provision lifecycle command.
- Marshall validates current ownership under a shared key lock and makes key ID
  part of idempotent Porsche request semantics.
- Public key bytes occur only in the sensitive key row, immutable operation
  snapshot and kernel command line; catalogued diagnostics contain none of them.
- Both images share a bounded parser, atomic installer and hardened sshd policy.
- Inception is excluded and terminal-v2 remains independent.
- Restart, clone and relocation deliberately preserve disk-local access. This is
  a consequence requiring explicit future rotation design, not implicit sync.
- A live Porsche clone exposed that Lilly's durable command store initially
  treated the required provision-to-lifecycle removal of `ssh_public_key` as an
  immutable identity conflict and fenced the host control channel. The corrected
  transition permits only that one-way removal. Introducing, restoring or
  changing bootstrap key material remains an identity conflict, and the protocol
  still rejects the field on non-provision commands.
- Audi's production staging-ACME configuration initially validated staging
  certificates against the production root set. Commit `9951321` supplies the
  four pinned staging roots only to Audi. The Dungarees gateway and DNS service
  identities were also absent from the fresh Marshall database and were restored
  through the reviewed operator actions. These were rollout defects, not a new
  certificate or service-authority boundary.
- Live Ubuntu boots exposed three independent image defects: masking
  `sshd.service` also masked Ubuntu's intended `ssh.service` alias; the service
  condition raced the bootstrap key installer; and package activation retained
  an `ssh.service.requires/ssh.socket` link after socket activation was masked.
  Commits `44c8a27`, `1344b8e` and `3f44d86` respectively keep the service
  available, evaluate the key after its required bootstrap unit, and remove the
  masked socket dependency. The machine fixture now requires an actual active,
  listening keyed Ubuntu service while retaining the no-key denial cases.
- New image closures initially required a manual catalog restart. The catalog
  closure is now a systemd restart trigger, and two later deployments registered
  their new image digests without operator intervention.

## Verification evidence and gaps

The protocol, Porsche, Galileo, Lilly, Marshall and Audi precommit gates pass.
Marshall tests exercise key provenance, snapshot construction, public-view
redaction and cross-key replay conflict. Python static checks and Python/Nix
evaluation tests cover malformed, duplicate and replacement bootstrap attempts,
file modes, persisted-disk restart readiness and the two service configurations.
Both actual NixOS and Ubuntu guest image derivations build successfully.

Focused Lilly command-store tests reproduce the provision-to-stop transition,
pass across store reopen, and reject later key restoration and replacement.

Live acceptance used Porsche at `overalls.dev:22` with the operator's registered
RSA key. The two final VMs remain running:

Each first connection used the generated Audi `KnownHostsCommand` and accepted
only the returned guest ED25519 key. Strict reconnect then succeeded against the
private pinned file. Password-only authentication failed for both. A forwarding
probe opened a local listener and actively attempted to reach guest port 22;
neither guest returned an SSH banner, establishing server-side forwarding denial
rather than merely proving that the local listener could bind.

Porsche stop requests `95a3fcd6-4f34-4946-bea3-7123057d8221` and
`c3c6a7ef-5554-4c85-8cbd-76a98df2f01f`, followed by start requests
`c826ffb6-04e1-459f-ba62-731ae798cec7` and
`b3ea1165-40e6-4616-a48c-e8f1bb58c304`, all reached matching physical outcomes.
After restart, strict host checking accepted the same fingerprint, the original
disk marker remained, and the provisioned root key still authenticated on both
VMs. The fingerprints are distinct. Both VMs were left running.

The deployed source revision for the final image acceptance was `3f44d86`; a
subsequent coordinated maintenance activated `3065fa5`. That maintenance rotated
the Marshall database credential after an earlier diagnostic exposed it. All
consumers were stopped, the database and Marshall bundles were prepared together,
the PostgreSQL role was updated, and consumers were restored. A private probe
confirmed the values differ, PostgreSQL rejects the retired credential and accepts
the replacement, without emitting either value. The updater subsequently recorded
`3065fa5` healthy, its timer is active, public Marshall HTTPS is ready and no
systemd unit is failed.

Audi gateway, DNS and private status sockets all returned their exact affirmative
role responses. Galileo's Unix-socket `/health/ready` response was also affirmative
and revalidated the configured host identity with Marshall. Audi's systemd service
had zero restarts throughout the final observation.

The earlier redacted `process_crash` and `supervisor_report` events were resolved,
not suppressed. Commit `59de4c5` introduced a closed, atom-only component label;
`82aec4d` separated TLS upgrade from the HTTP handler, and `4fa5c95` separated
HTTP callbacks without retaining request data, hostnames, URLs, headers or raw
reasons. Live events then consistently identified `http_init`. Audi had already
read and validated the client peer on the raw socket before TLS, but after the
upgrade it called Bandit's HTTP/1 initializer, which queried `:ssl.peername/1`
again. A client closing in that narrow transition made Bandit raise a transport
error, producing two OTP crash reports and one supervisor report for an otherwise
connection-local close.

Commit `314e178` preserves the pre-upgrade peer and supplies Bandit's required
`{secure?, peer_address}` connection data directly. The regression passes an
intentionally unusable post-upgrade socket and proves initialization performs no
second peer lookup. The production updater activated that revision at
`2026-09-22T16:05:24Z`. Through `2026-09-22T16:12:59Z`, a window far longer than
the previous seconds-level failure cadence, Audi emitted zero `process_crash` and
zero `supervisor_report` events. Audi and Galileo remained active with zero
systemd restarts, all four readiness checks were affirmative, the updater's next
no-change run succeeded, and the host had zero failed units.

Strict pinned-host-key SSH to both retained VMs again authenticated as root and
found each original persistent marker; both guests remain running. The development
VM maps `overalls.dev` to loopback, so its generated profiles could not perform
their HTTPS host-key lookup without an explicit public-IP resolution override.
The override still used the reviewed HTTPS endpoint and pinned guest host keys;
it changed no deployed configuration and was removed after the checks.

The final diff preserves ADR-0093's boundaries: no new public route or mutable
key synchronization was introduced, and the persisted-key service condition is
required for the decided restart behavior. The real KVM and Audi acceptance now
covers both distributions, strict reconnect, distinct host identities, password
and forwarding denial, and stop/start persistence. ADR-0093 is implemented.

Focused image builds, the Ubuntu unit check, both Overalls configuration
evaluations, secret inventory validation, contract discovery and whitespace checks
passed during the live repair sequence. The native nested-KVM check could not run
on the development VM because its Nix daemon does not declare the `nested-kvm`
feature; the live Firecracker acceptance above supplies the milestone evidence but
does not misrepresent that local check as passed. Final repository-wide gates are
recorded with the completing commit.
